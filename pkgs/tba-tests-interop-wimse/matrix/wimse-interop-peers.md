# WIMSE interoperability peers and capabilities

The matrix uses one catalog with 15 entries, including two combined-profile slots that resolve to wimsey in the lab. An implementation can fill multiple roles and appear in more than one section. The **Source** column identifies the provider of the implementation or binding. A runtime qualification records the implementation, version, configuration, and role. Workload calls also record the exact caller and receiver tested together. [Peer catalog](../src/tba_tests_interop_wimse/peers.toml) · [How participants and roles map to hops](wimse-interop-guide.md#entities-peers-roles-and-capabilities)

## Workload calls

WIC supplies the certificate identity for mTLS. WIT supplies the application-layer credential. WPT and HTTP Message Signatures supply application proof. A combined profile checks both layers. WIMSE and SPIFFE in the **WIC identifiers** column refer only to the certificate identity, so an application-only profile shows an em dash there. The issuer of the WIT is selected separately for each hop. [Profiles and factors](../src/tba_tests_interop_wimse/factors.toml)

## Status and policy checks

Use the per-ID report to see whether the request reached the peer assigned to the check and what the runner observed. ## RICH workload roles and named nine-hop assignments

| Binding | Caller proof | Receiver proof | Qualified scope |
| --- | --- | --- | --- |
| RICH Coordinator | WIT + HTTP Message Signatures | WIT + HTTP Message Signatures | Generic control in both directions with TbA, plus the named Coordinator role |

The roles share the pinned RICH revision and have distinct workload identities. See the [nine-hop substitution table](wimse-interop-rich-nine-hop-qualification.md#role-substitutions) for the complete list of eligible bindings per participant, including the reference fixtures.
